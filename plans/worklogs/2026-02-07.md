### 13:13 - OpenSearch migration analysis and architecture design
**Author:** dinnyosz

#### Completed
- Deep exploration of current Elasticsearch usage across the Magaldi codebase: client version (`elasticsearch[async]==8.11.0`), index mappings (`dense_vector`, nested fields), query types (bool, match, multi_match, function_score, script_score, knn), bulk operations, and async patterns
- Web research on OpenSearch capabilities: hybrid search (combining BM25 + k-NN in a single query), neural sparse search, ML Commons framework, k-NN engines (Faiss/Lucene/NMSLIB), search pipelines with reranking, anomaly detection, PPL query language, alerting
- Python client migration assessment: `opensearch-py` is a near-trivial swap from `elasticsearch-py` — same API surface, same bulk helpers, same async support
- Created comprehensive migration analysis document covering all aspects of moving from Elasticsearch to OpenSearch
- Designed interface-driven architecture with `SearchBackend` Protocol for pluggable backends — repositories never import client libraries directly
- Documented full Elasticsearch purge plan: 43 source files and 7 test files with exact class/variable rename tables
- Outlined 5-phase implementation approach with risk assessment for both migrating and not migrating

#### Decisions Made
- **Migration IS beneficial** — Apache 2.0 licensing, native hybrid search, ML Commons, and neural sparse search are the key wins over Elasticsearch
- **Interface-driven architecture** chosen over simple compatibility shim — a `SearchBackend` Protocol allows future backend swaps (pgvector, Qdrant, etc.) without touching repository code
- **Clean break with ES naming** — no "dual support during migration" period; once OpenSearch is battle-tested, purge all `Elasticsearch*` naming from codebase
- **Config key changes** from `elasticsearch:` to `search_backend:` with a `type` selector field (`opensearch`, `elasticsearch`)
- **OpenSearch as primary**, Elasticsearch as optional compatibility backend behind the interface
- **Factory pattern** for backend instantiation from config

#### Notes

  5. **k-NN engine choice** — Faiss HNSW for better recall/speed tradeoffs vs current Lucene HNSW

#### Decisions Made
- **Asymmetric embeddings**: Keep `summary_embedding` (passport) pure for semantic search. Add new `context_embedding` enriched with outbound calls for Strategy 6 call resolution. Caller uses `context_embedding`, candidate uses `summary_embedding`.
- **Revert calls from passport**: Calls will be removed from `build_summary_embedding_text()` for both files and functions/methods, moved exclusively to `build_context_embedding_text()`
- **Optimization**: Elements without calls reuse `summary_embedding` as their `context_embedding` (identical text = identical vector, saves an embed call)
