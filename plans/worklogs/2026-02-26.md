### 22:25 - GSS bracket protection, nearest-data narrowing, and peak re-evaluation

**Author:** dinnyosz

#### Completed
- Fixed GSS bracket permanently excluding the optimal level by adding bracket expansion (Step 0) — when the best-performing level is outside the bracket, it expands to include it
- Added `_nearest_data()` helper for fuzzy ±2 matching during bracket narrowing — allows narrowing even when data isn't at exact golden-ratio probe points
- Protected best-known level during narrowing — `lo` can never go above it, `hi` can never go below it, preventing GSS from discarding the optimal region
- Fixed infinite loop in narrowing `while` loop — replaced with `for` loop capped at 20 iterations, added break guards when no progress is made, and log-only-on-change to prevent log spam (previous bug produced 18.9M log lines)
- Added post-convergence peak re-evaluation — after GSS converges, `best_level` updates dynamically if new qualified level data shows a better base_time
- Killed zombie pytest process (PID 47127) that was filling `/tmp/throttle.log` at 99% CPU with old infinite-loop code
- Deleted stale `.pyc` bytecache that was serving old compiled code despite `pip -e` install
- All 152 throttling tests passing, lint clean

#### Decisions Made
- Replaced exact-match narrowing with fuzzy ±2 `_nearest_data()` — allows GSS to narrow using nearby level data instead of requiring data at exact golden-ratio probe points. Uses `min(matched_level, geometric_point)` for tighter boundaries to prevent bracket expansion from fuzzy matches.
- Added bracket expansion before narrowing (Step 0) — GSS was a one-way narrowing system that could never recover from early bad decisions. Now it expands to include the best-known level before narrowing.
- Changed narrowing from `while` to `for` with cap of 20 — prevents infinite loops even if break guards fail. Added log-only-on-change to prevent log spam.
- Peak re-evaluation post-convergence done in `parallel_processor.py` not `throttling.py` — because `parallel_processor` has access to the live `level_data` dict and owns the throttle context lifecycle.

#### Open Questions
- GSS narrowing uses ±2 radius for nearest-data matching — is this too aggressive for steep performance curves? Could be reduced to ±1 if problems arise.
- The bracket expansion + narrowing protection means GSS effectively becomes "find the best level" rather than true golden-section search. If the performance curve is noisy, the bracket may oscillate. May need a stability threshold (e.g., only expand if the outside level is significantly better, not just marginally).

#### Notes
- Python `.pyc` bytecache can serve stale code even with `pip install -e` — the pyc was newer than the source file, so Python used it. Need to be aware of this when editing files that are being actively used by running processes.
- The `_log_throttle` function writes to `/tmp/throttle.log` with no rotation — infinite loops can fill disk quickly. The for-loop cap is a critical safety net.
- The old narrowing code had a subtle bug: bracket [7,13] with m1~8 (bt=1.00) and m2~13 (bt=6.00) would try to set `hi=m2=13` which equals `self.hi=13` — no progress, but no break guard either, causing infinite loop.
