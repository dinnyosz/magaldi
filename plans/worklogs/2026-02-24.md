### 14:58 - Deep dive into variable filtering -> LLM-based scoring design
**Author:** dinnyosz

#### Completed
- Deep dive into the entire variable filtering system across all 5 language extractors (Python, JS/TS, PHP, Rust, Bash)
- Identified 6 gaps in the current heuristic-based usefulness filter:
  1. `is_useful_value_type()` never returns False (dead code path)
  2. Useful factory calls kept by fallthrough, not explicit path (fragile)
  3. Bash has zero variable filtering
  4. Python has a separate `is_useful_assignment()` that can drift from shared filter
  5. JS/PHP `walk_tree` extracts function-body variables but marks them `is_module_level=True`
  6. Inverted return semantics between the two filter APIs
- Discussed fundamental approach -- concluded heuristic filter is wrong tool for a semantic question
- Designed new approach: LLM-based variable scoring as new Phase 4 in the pipeline
- Created and got approval for implementation plan at `plans/glimmering-mixing-charm.md`

#### Decisions Made
- Replace entire heuristic usefulness filter with LLM-based variable scoring (new Phase 4)
- Extract variables at ALL depths in ALL languages (function bodies, class methods, everywhere) -- not just top-level
- Low-scoring variables are dropped entirely (not indexed at all) -- saves the most resources
- Dynamic batch sizing: estimate token count per variable, fill batches up to tier capacity
- Use existing `SummarizationLLMClient` with small model for scoring
- Current Phase 4 (summarize->embed->index) becomes Phase 5, all subsequent phases shift +1
- Scoring dimensions: config_value, architectural_role, data_definition, general_usefulness (each 1-10)
- Threshold: if ANY dimension >= 5, variable passes to Phase 5
