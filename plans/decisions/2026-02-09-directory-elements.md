## Decision: Directory elements as a new element type

**Original plan:** Magaldi indexes code elements (functions, classes, methods, etc.) and files. There is no concept of directory-level elements in the data model. Navigation and discovery rely on individual element search and feature extraction for semantic grouping.

**Deviation:** Treat directories as elements, processing them bottom-up (deepest paths first), where each directory summary is an aggregation of its contained file summaries + subdirectory summaries. This creates a recursive rollup from leaf directories to the repo root.

**Why:** The biggest value is for MCP tools where `search_code("database layer")` could return `src/shared/db/` with a high-level summary before diving into individual elements. Directory elements provide structural/organizational groupings that complement the semantic groupings from feature extraction. They give users a "zoom out" capability to understand what a module or package does at a glance.

**Options considered:**

1. **Full automatic directory elements** — Always compute directory summaries during every parse run
   - Pros: Always up-to-date, complete hierarchical view
   - Cons: High LLM cost (cascade of summarization calls on every change), staleness issues (single file edit cascades up through many levels), adds noise to search results

2. **Opt-in directory elements (like --features/--glossary)** — Add a `--directories` flag, process lazily, skip trivial single-file directories
   - Pros: User controls cost, only generated when wanted, can be selective about depth
   - Cons: Extra CLI flag, not always fresh

3. **No directory elements** — Rely on existing feature extraction to group code semantically
   - Pros: No additional cost, features already cluster related code
   - Cons: Misses structural/organizational groupings, no module-level navigation

4. **Static directory elements without LLM** — Just aggregate file names and element counts, no AI summary
   - Pros: Zero LLM cost, fast, always accurate
   - Cons: Much less useful than semantic summaries

**Final decision:** Option 2 — Opt-in with `--directories` flag, bottom-up recursive processing, lazy (skip trivial directories). This aligns with the existing pattern of opt-in enrichment phases (`--features`, `--glossary`). Directory summaries would be generated by aggregating child file and subdirectory summaries through the LLM, only when explicitly requested.

**Status:** Design discussion only — no implementation started. This is a future enhancement to consider.
