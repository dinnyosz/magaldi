# Architecture Decision Record: ES+Redis Architecture

**Date:** 2026-01-06
**Status:** Accepted
**Context:** CLI implementation with real persistence

---

## Decision 1: Use Elasticsearch for Change Detection

### Context
Originally, change detection used MySQL to store file states (path + hash). However, a data consistency issue was discovered: MySQL could report files as "unchanged" while Elasticsearch had no indexed data for those files.

### Decision
Move change detection to Elasticsearch by storing `file_hash` on file-level elements.

### Rationale
- **Data consistency**: If ES doesn't have the file indexed, change detection correctly reports it as needing parsing
- **Single source of truth**: No separate state tracking that can get out of sync
- **Simpler architecture**: One less data store to maintain for this purpose

### Implementation
- Added `file_hash` field to ES index mapping
- Created `ElasticsearchFileStateRepository` class
- Query ES for existing file elements and their hashes

## Decision 2: Remove MySQL Entirely

### Context
After moving change detection to ES, MySQL was only used for:
- `file_states` table (now in ES)
- `code_elements` table (duplicated in ES)
- `summarization_jobs` table
- `embedding_jobs` table

### Decision
Remove MySQL from the architecture completely. Use ES for storage and Redis for job queues.

### Rationale
- **Reduced complexity**: One less database to deploy, configure, and maintain
- **Simpler deployment**: Only need ES and Redis containers
- **No data duplication**: Elements stored once in ES, not twice
- **Cost reduction**: Fewer services to run

### Trade-offs Considered
- MySQL provides ACID transactions (Redis provides atomic operations, sufficient for job queues)
- MySQL has mature tooling (Kibana provides ES visualization)

## Decision 3: Use Redis for Job Queues

### Context
Needed a replacement for MySQL job tables after removing MySQL.

### Decision
Use Redis sorted sets and hashes for summarization and embedding job queues.

### Rationale
- **Purpose-built for queues**: Redis sorted sets provide natural priority ordering
- **Atomic operations**: `ZADD`, `ZPOPMIN` are atomic
- **High performance**: In-memory operations ideal for job claiming
- **Already in stack**: Redis was already planned for caching

### Implementation Details

**Summarization Jobs:**
- Sorted set with score = `level * 1000 + priority` (process leaves before parents)
- Hash stores job metadata (parent_id, dependencies_met, retry_count)
- Uses `ZPOPMIN` for atomic claim

**Embedding Jobs:**
- Sorted set with timestamp score (FIFO ordering)
- Simpler than summarization (no dependency tracking)

**Summary Store:**
- Hash for temporary storage during processing
- Workers write summaries here, then batch update ES

## Decision 4: File Hash Storage Location

### Context
Need to store file content hashes for change detection without a separate MySQL table.

### Decision
Store `file_hash` as a field on file-level elements in Elasticsearch.

### Rationale
- **Co-located with data**: Hash lives with the indexed content
- **No separate lookup**: Single query gets both file existence and hash
- **Automatic cleanup**: When file element is deleted, hash goes with it

### Implementation
```python
# In index mapping
"file_hash": {"type": "keyword"}

# Only set on file-level elements (level 0)
if element.element_type == "file":
    search_repo.index_element(element, indexed_at, file_hash=file_hash)
```
